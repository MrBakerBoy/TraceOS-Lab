## 一、文档说明

本文档按照大赛技术方案中关于 AI 工具使用的评审要求，如实、完整地记录 SyncGenesis 队伍在 TraceOS Lab 项目开发过程中使用 AI 工具的情况。

TraceOS Lab 项目经过的完整开发周期，历经 v0.9 原型期 → v1.0 赛题基线 → v1.5 教学创新 → v2.0 架构收敛四个版本，最终形态为 **4 个微服务、460+ 源文件**（Go 153 / Python 115 / TypeScript 258 / eBPF C 11 / SQL 27 迁移）的完整平台。

在整个开发周期中，我们始终坚持 **"人主导一切设计决策、AI 辅助编码提速、全程人工验证"** 的原则：

- **项目的绝大部分任务由队员完成**：系统架构、技术选型、核心算法、安全策略、教学模型、质量治理等全部关键工作均由队员自主设计、实现与决策；
- **AI 的定位是编码提速工具**：AI 主要用于样板代码生成、重复性代码编写、初稿起草、编译错误批量定位等"体力型"编码环节，为队员节省时间；
- **每一行代码都经过人工把关**：AI 生成的所有内容必须经过队员逐行审查、修改、测试后方可合入，AI 不替代队员承担任何设计与质量责任。

本文档涵盖以下内容：

- 使用的 AI 工具与模型清单
- AI 辅助完成的具体工作与范围
- 人工修改、重构与验证的完整流程
- AI 生成内容中的典型错误及人工发现/修正过程
- 队伍对全部代码设计逻辑的掌握说明

| 工具名称 | 类型 | 主要用途 | 使用阶段 |
|---------|------|---------|---------|

### 2.2 调用的大语言模型

| 模型名称 | 提供方 | 主要用途 |
|---------|-------|---------|
| **DeepSeek-V4-Pro** | DeepSeek | 复杂业务逻辑讨论、Go 后端代码生成、评测引擎算法设计讨论 |

### 2.3 使用原则

所有 AI 工具的使用均遵循以下三条红线：

1. **方案决策权在人**：系统架构选型、技术栈组合、模块划分、安全策略、评分模型、教学模型等关键决策均由队员讨论确定。项目沉淀的 **12 条 ADR（架构决策记录）全部由队员人工拍板**，AI 仅提供参考意见，不替代队伍做任何设计层面的选择。
2. **所有 AI 输出必须经过人工审查**：AI 生成的每一段代码在合入项目之前，必须经过队员的逐行阅读、逻辑验证和本地运行测试。项目最终形态中的代码，无论最初由谁起草，都经过队员的完整审查与修改。
3. **队伍必须能够脱离 AI 独立维护系统**：每位队员均要求能够在无 AI 辅助的条件下，独立解释所负责模块的设计原理、数据结构、关键算法和边界条件。

## 三、AI 辅助完成的工作范围与人工贡献对照

### 3.1 总体分工概览

TraceOS Lab 项目最终代码规模为 **460+ 源文件**（Go 153 / Python 115 / TypeScript 258 / eBPF C 11 / SQL 27 迁移），涵盖 4 个微服务（core-service / ai-service / observability / frontend）、31 个预置实验、21 个 OS 语义模式、27 个数据库迁移的完整评测与教学链路，累计 2694 次提交。

**总体判断：项目绝大部分工作由队员完成，AI 主要在编码环节提速。** 分工作类别的具体对照如下：

| 工作类别 | AI 参与程度 | 人工主导程度 | 说明 |
|---------|:---:|:---:|------|
| **系统架构设计** | 5% | **95%** | 4 服务边界、事件驱动链路、双轨观测等全部由队员设计，AI 仅用于讨论和方案对比 |
| **技术选型** | 10% | **90%** | 队员调研后决策，AI 辅助提供各方案的优劣势对比 |
| **核心算法实现** | 20% | **80%** | 评分模型、语义建模、死锁状态机等由队员设计算法流程，AI 辅助生成实现初稿 |
| **业务逻辑代码** | 30% | **70%** | AI 生成初始代码，队员审查、修改和优化 |
| **样板代码/CRUD** | 55% | **45%** | AI 大幅提升编码速度，但队员逐一验证逻辑正确性 |
| **测试用例编写** | 35% | **65%** | AI 生成测试框架，队员设计断言口径、补充边界用例并验证 |
| **前端 UI 组件** | 40% | **60%** | AI 生成组件骨架，队员设计交互、状态管理与可视化方案 |
| **数据库 Schema** | 20% | **80%** | 27 个迁移的数据模型全部由队员设计，AI 辅助生成 DDL |
| **配置文件/Docker** | 45% | **55%** | AI 生成模板，队员根据实际部署需求调整 |
| **文档编写** | 25% | **75%** | 12 篇专业技术文档的技术内容全部由队员撰写，AI 辅助表达润色 |
| **Bug 定位与修复** | 20% | **80%** | 队员分析根因，AI 辅助提供排查思路和批量修复建议 |
| **代码审查** | 15% | **85%** | AI 标记潜在问题，队员独立判断是否采纳 |

综合统计，AI 在整个项目中的参与度约为 **25%**，且集中体现在"编码提速"环节；**设计、决策、验证、质量把关等 75% 以上的工作由队员独立完成**。

3. **九大里程碑的架构判断**：4 服务边界的首日确定、"观测先行"的优先级决策、v2.0 收敛策略等；

5. **安全策略设计**：三级沙箱、6 套 seccomp 白名单、Prompt 注入防护、Context Firewall；
6. **教学质量模型设计**：L1-L4 渐进反馈、六维能力画像、rubric 教学注释体系。

## 四、AI 生成内容的验证与修改流程

### 4.1 标准工作流

每位队员在开发过程中遵循以下标准流程：

```
队员构思设计思路
    │
    ▼
编写设计文档 / 伪代码 / 接口定义
（重大升级先写 plan 文档，再动手实现）
    │
    ▼
向 AI 工具提出具体、有约束的请求
（明确技术栈、代码风格、边界条件、错误处理要求）
    │
    ▼
审查 AI 生成的代码：
├─ 逐行阅读，理解每一行逻辑
├─ 检查类型安全、错误处理、边界条件
├─ 对照设计文档验证功能完整性
└─ 标记可疑、冗余或不合理之处
    │
    ▼
本地运行与测试：
├─ 单元测试 / 集成测试（Go test / pytest / vitest）
├─ 手动边界用例验证
└─ e2e 全链路验证（e2e_test_round.sh）
    │
    ▼
人工修改与优化：
├─ 修复 AI 生成代码中的错误
├─ 重构不合理的设计
├─ 统一代码风格
└─ 添加 AI 未考虑的边缘情况处理
    │
    ▼
Code Review（队员交叉审查）
    │
    ▼
合入主分支
```

### 4.2 人工修改统计

项目累计 **2694 次提交**，其中绝大多数为队员的人工设计、实现、修复与治理提交。AI 生成代码引入后的典型人工修改类型统计如下：

| 修改类型 | 典型提交/工作 | 说明 |
|---------|------------|------|

## 五、AI 生成代码的典型错误与人工修正案例

以下是开发过程中遇到的 AI 生成代码的典型问题，以及队员如何发现和修正的真实案例。

### 案例 1：前端组件 JSX 展开语法错误

- **AI 生成内容**：Sidebar 组件中使用了错误的 JSX 展开语法，将非标准对象属性传递到 DOM 元素，导致 React 运行时抛出大量控制台警告和渲染异常。
- **发现方式**：队员在本地 `pnpm dev` 运行时，浏览器控制台出现 15+ 条 React 警告。逐组件排查后发现 Sidebar 的 props 传递链路存在问题。
- **修正过程**：队员完整重写了 Sidebar 组件的 props 接口定义和传递逻辑，移除了不规范的属性展开，明确了每个 DOM 元素允许接收的属性。

### 案例 2：前端页面使用了不存在的组件 API

- **AI 生成内容**：多个前端页面引用了 AI 虚构的 UI 组件 API（不存在的 Props 名称、错误的事件处理器签名），导致 TypeScript 编译失败，共 20+ 个类型错误。
- **发现方式**：队员运行 `pnpm build` 时 TypeScript 类型检查报错。AI 生成的代码基于过时的组件库版本，与项目实际安装的版本不匹配。
- **修正过程**：队员逐文件检查错误信息，对照组件库的实际 API 文档，逐一修正 Props 名称和函数签名。对于 AI 虚构的组件，替换为项目中已有的等效实现。

### 案例 3：Sscanf 对 map 取地址的 Go 语法错误

- **AI 生成内容**：在 strace 解析器中，AI 生成了对 map value 取地址的代码（`&m[key]`），这在 Go 中是不允许的——map 的元素不可寻址。
- **发现方式**：队员在 `go build` 时遇到编译错误。AI 不了解 Go 语言的 map 内存模型限制。
- **修正过程**：队员使用临时变量接收 Sscanf 结果后再赋值给 map，同时添加了错误码的范围校验。

### 案例 4：Go 包引用遗漏

- **AI 生成内容**：在沙箱预热池实现中，AI 生成的代码使用了 `time` 包的相关函数，但 import 声明中遗漏了 `"time"` 包的引用。
- **发现方式**：`go build` 编译报错。
- **修正过程**：队员补充缺失的 import，并系统性检查同模块所有文件的 import 完整性。

### 案例 5：AI 生成代码中的安全漏洞

- **AI 生成内容**：
  - `.env` 文件中包含了硬编码的 LLM API Key
  - CORS 配置使用了 `AllowOrigins: ["*"]` 全通配符
  - JWT Secret 使用了默认值且无启动校验
- **发现方式**：队员在进行安全审查时逐文件检查了敏感信息，发现了 5 项 P0 级别安全隐患。
- **修正过程**：
  - 移除所有硬编码密钥，改为环境变量 + 启动时验证
  - CORS 改为仅允许配置的 `FRONTEND_URL`
  - JWT Secret 添加启动时默认值检测和强警告

### 案例 6：诊断缓存 Key 设计缺陷

- **AI 生成内容**：诊断服务的内存缓存仅使用 submission_id 作为 key，导致不同测试用例的运行结果可能命中错误的诊断缓存。
- **发现方式**：队员在编写诊断服务的测试用例时，发现连续两次提交不同代码却返回了相同的诊断结果。通过阅读 `diagnosis_service.py` 源码，定位到缓存 key 设计过于简单。
- **修正过程**：队员重新设计了缓存 key，加入 test_results 的 JSON 序列化和 strace_summary 的哈希值，确保不同运行结果的缓存隔离。

### 案例 7：AI 生成的 TypeScript `any` 类型泛滥

- **AI 生成内容**：API 客户端 `api.ts` 中大量使用 `any` 类型，失去了 TypeScript 的类型安全保障。
- **发现方式**：队员通过 `tsc --noEmit` 检查发现了 30+ 个隐式 `any` 类型警告。
- **修正过程**：队员完整重写了 API 客户端，定义了 20+ 个类型接口（User、Experiment、Submission、DiagnosisResult、TestCase 等），为每个请求/响应添加了精确的类型标注。

### 案例 8：v2.0 撤回 AI 辅助评分——评分确定性的原则坚守

- **AI 参与背景**：v1.5 版本曾引入"AI 辅助评分 ±15 分微调"机制，AI 生成的相关代码已合入系统。
- **发现方式**：队员在 v2.0 收敛期对照"评分必须确定性"这一架构原则进行系统复查，发现 AI 辅助评分引入了大模型的随机性，违背了评分公平底线。
- **修正过程**：队员独立决策并执行撤回（ADR-001：评分与诊断职责分离，永不回退），删除了 AI 评分路径的全部代码，确立"AI 只解释不判分"的红线。这一决策体现了队员对架构原则的独立坚守——即使 AI 生成的代码"能用"，不符合原则也坚决移除。

### 案例 9：死锁检测的误报问题——从 bpftrace 到 strace 的独立重构

- **AI 参与背景**：初版死锁检测基于 bpftrace + AI 生成的 futex 追踪框架，在容器内不可用，且对正常多线程程序存在大量误报。
- **发现方式**：队员用真实多线程程序测试时发现误判死锁的问题——正常程序被标记为死锁，而真正的死锁在容器内无法捕获。
- **修正过程**：队员独立完成系统性重构：bpftrace 切换为 strace 以兼容容器环境；死锁状态机重新设计为"延迟到进程退出时才判定"，消除运行中误报；通过 trace clone/exit 事件注册全部线程修复锁图完整性。这一轮攻坚证明：**误报摧毁教学信任的速度远快于漏报**。

### 案例 10：依赖残留与可复现性治理

- **AI 参与背景**：早期 AI 生成代码引入了 LangGraph/ETCLOVG 等框架依赖，torch 依赖了外网源，导致从零构建失败。
- **发现方式**：队员在第 8 周收敛期进行依赖清单审计与从零构建验证时发现。
- **修正过程**：队员独立完成清理——移除 LangGraph/ETCLOVG 残留并简化为顺序管线，恢复 torch 的 CPU 源从零构建能力。"能跑"不等于"可复现"，依赖引入要慎重、退出要彻底。

## 六、队伍对系统核心设计的掌握说明

### 6.1 架构设计（队员自主完成）

以下关键架构决策由队员经过调研、讨论后独立确定，AI 未参与决策（全部沉淀为 12 条 ADR）：

1. **四服务边界拆分**：core-service（评测事实中心）/ ai-service（教学智能中心）/ observability（观测读侧）/ frontend（双端交互入口）——按安全边界、故障边界、扩容边界、技术栈边界四重标准切分；
2. **评分与诊断职责分离**：AI 只解释不判分，评分确定性与 AI 随机性彻底隔离；
3. **观测双轨架构**：eBPF（CO-RE 主链路）+ strace（降级兼容），保真度与可用性兼得；
4. **三层沙箱隔离策略**：Standard → Secure → Hardened 的分级方案 + 6 套 seccomp 白名单；
5. **事件驱动评测链路**：基于 NATS JetStream 的异步评测与诊断触发，AI 故障不影响评分主链路；
6. **ObsContext 三层语义建模**：原始事件 → 结构化系统调用 → OS 语义（21 个模式库）；
7. **多 Agent 诊断 Harness 五层治理**：证据锚定、评分隔离、上下文治理、可审计、可降级；
8. **混合检索 RAG**：BM25 + 向量 + 五级 Embedding 降级链；
9. **多模态存储**：PostgreSQL + TimescaleDB + pgvector 三合一 + Redis + MinIO；
10. **v2.0 三条红线**：评分确定性、观测双轨、AI 不碰真值。

### 6.3 关键数据结构与算法掌握

队伍每位成员均能就以下核心设计与实现进行无 AI 辅助的独立讲解：

- **评测 Pipeline**：编译 → 沙箱执行 → 双轨观测 → 断言评分 → 事件发布的 8 步流程，以及各步骤之间的 context 传递和错误处理策略；
- **五类断言评测体系**：输出断言、行为断言（syscall 模式）、模式断言、资源断言、时序断言的判定口径，core 门槛 + edge 加权的评分模型设计依据；
- **eBPF 双编译加载器**：CO-RE 编译路径、HASH_OF_MAPS 沙箱隔离机制、syscall/futex/mem 三类 BPF 程序的挂载点与事件流；
- **ObsContext 三层语义建模**：原始事件归一化 → 结构化系统调用抽象 → 21 个 OS 语义模式的识别规则与置信度；
- **多 Agent 诊断 Harness**：确定性 Planner + 5 Specialist 的拓扑、条件路由、Context Firewall 的上下文裁剪策略、L1-L4 渐进反馈的 Prompt 设计原理；
- **死锁检测状态机**：futex 追踪、进程退出延迟判定、锁图 hold 关系维护；
- **RAG 混合检索与五级降级**：BM25 稀疏检索 + 向量稠密检索的融合策略、Embedding 五级降级链（在线 API → 本地模型 → TF-IDF）；
- **前端可视化中枢**：Zustand 全局状态设计、SSE/WebSocket 双通道推送、Three.js 内存 3D 与火焰图渲染的数据契约。
